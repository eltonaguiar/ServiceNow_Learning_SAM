Start in five minutes

  1. Get a free instance at developer.servicenow.com.
  2. Run the read-only probe (scripts/sn_probe.js from the main kit) in System Definition > Scripts - Background.
  3. Score the instance: python3 scripts/sam_readiness.py probe.json.
  4. If it says NOT READY, the scorecard's last column is your work queue.
  5. If it says READY, go straight to the lab.

The three hard gates

Missing any of these makes every number downstream fiction — no matter how tidy the configuration looks.

1 · Schema + entitlement

samp_* / cmdb_sam_* tables present. SAM Foundation and SAM Professional are different products — decide which one you are implementing before step one.

2 · CMDB, with identification rules

Duplicate CIs double-count installs. Configure CI identifiers before loading data. These are a CMDB/IRE mechanism, not SAM configuration — answered in full under identification rules vs normalisation.

3 · A discovery feed

SCCM, Intune, Jamf, Agent Client Collector or a Service Graph Connector. Hand-typed installs make an asset register, not software asset management.

Identification rules vs normalisation — which applies where

This is the most misattributed control in SAM, and the answer is: HAM yes, SAM indirectly.

MechanismAnswersConfigured inApplies to
CI identification rules (IRE)Is this CI new, or the one I already have?CI Class Manager / CI IdentifiersCMDB — all CIs incl. every server and laptop; this is what HAM relies on
Asset↔CI reconciliationWhich asset record is this CI?HAM asset sync on serial numberHardware assets ↔ hardware CIs
Normalisation / recognitionAre these two software titles the same product?SAM content library / publisher packsSAM — its real identity problem
Licence metricPer user, device or core?Entitlement recordSAM — commercial decision
Licence reconciliationRights vs installs → complianceSAM reconciliationSAM — the number you defend

HAM: directly — one laptop seen by SCCM, Intune and a manual import must resolve to one CI, usually on serial number. SAM: there are no identification rules for software products (you normalise instead), but every install record hangs off a CI, so duplicate CIs duplicate installs and inflate the gap. Fix computer-class identification before reconciling.

Rule of thumb: deduplicating a machine → CMDB/IRE. Deduplicating a software title → normalisation in SAM. Deduplicating a quantity of rights → a licence metric, which is a commercial decision.

The scorecard turns these into pass/warn/fail with a next action per row, and caps the grade when a hard gate fails — deliberately, because a confident number built on missing discovery is worse than no number.

# → 50/100 — NOT READY — a hard prerequisite is missing

Prerequisites checklist

  • Foundation data loaded — company, locations with time zones, departments, cost centres, users and groups; SAM's spend dimensions are these fields
  • Entitlement and plugin (Foundation vs Professional decided)
  • Asset manager, SAM admin roles, plus a non-human integration user
  • One working discovery feed, scoped to a pilot
  • CMDB identification rules configured before any load — a CMDB/IRE task, not SAM
  • Content library / publisher packs reachable
  • Licence metric decisions written down and signed by the commercial owner
  • Contract and purchase-order data, or a plan to obtain it
  • A named owner for the reconciliation output

Three or more missing? The next hour belongs to prerequisites, not to forms.

Three kinds of "required" exist: dictionary-mandatory (survives APIs and imports), UI-policy-mandatory (form only) and data-policy-mandatory. Only the first is safe to rely on — the probe prints your instance's dictionary view.

The lab

Three titles, three licence metrics, one defensible number

Build a compliance position for one per-device title, one per-user title and one per-core title. Then change a single metric and watch the answer flip — the moment SAM stops being data entry. Part 0-B covers instances with no SAM entitlement, so the reasoning is learnable on a PDI.
